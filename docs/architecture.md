 # 🏗️ Architecture Rules (프로젝트 초기부터 적용)

  ## 1. 파일 크기 제한
  - 단일 파일 **최대 300줄**. 초과 시 반드시 분리.
  - 분리 기준: UI 렌더링 / 비즈니스 로직 / 상수·타입 / 유틸리티
  - 300줄이 넘는 파일을 생성하지 말 것. 처음부터 분리해서 작성.

  ## 2. 디렉토리 구조: 도메인 기반
  - 기능별 디렉토리로 구성. flat 구조 금지.
  - 예시:
    - `services/stock/`, `services/auth/` (백엔드)
    - `components/settings/`, `components/economic/` (프론트엔드)
  - 새 도메인 추가 시 디렉토리부터 생성.

  ## 3. 관심사 분리 (Separation of Concerns)
  - **UI 컴포넌트**: 렌더링만 담당. 상태 관리·API 호출 금지.
  - **커스텀 훅/서비스**: 상태 관리, API 호출, 비즈니스 로직 담당.
  - **상수·타입 파일**: 설정값, 매핑 테이블, 타입 정의 분리.
  - 하나의 파일이 fetch + state + render를 모두 하면 안 됨.

  ## 4. 중복 금지 (DRY at creation time)
  - 동일 로직이 2곳 이상에서 필요하면, **작성 시점에** 공유 모듈로 추출.
  - "일단 복붙하고 나중에 정리" 금지. 처음부터 공유 파일 생성.
  - 공유 대상: 유틸 함수, 훅, 상수, UI 컴포넌트 모두 포함.

  ## 5. Import 규칙
  - 절대 경로 import만 사용 (예: `@/`, `app.` 등 프로젝트 alias).
  - 상대 경로 `../` 사용 금지. 같은 디렉토리 내 `./`만 허용.

  ## 6. 코드 품질 도구: 첫 커밋 전에 설정
  - Linter + Formatter를 프로젝트 초기화 시 반드시 설정.
  - pre-commit hook으로 자동 실행되도록 구성.
  - 코드 작성 전에 도구부터 세팅.
